📋 sb3gen マスターサマリー

自然言語指示 → Scratch .sb3 自動生成パイプライン（現在地）

1. 全体アーキテクチャ
run.py（CLI・LLMプロバイダ選択・リトライ）
   └─ sb3gen.main.generate_sb3()  ← 統合エントリーポイント
        │
        ├─ patcher.py    … 指示解析・実行計画・アクション実行（オーケストレーション中枢）
        │     ├─ llm_io.py  … LLM呼び出しの安定化（JSON検証・分割生成）
        │     ├─ renderer.py … ProjectSpec → 疑似コード（差分指示のコンテキスト提示用）
        │     ├─ linter.py  … 未定義変数/リスト/ブロードキャストの自動グローバル登録
        │     └─ schema.py  … Pydanticデータモデル・opcode許可リスト・整合性検証
        │
        ├─ assets.py     … コスチューム/サウンドのアセット生成・登録・テンプレート管理
        │
        ├─ compiler.py   … ProjectSpec（高レベルIR） → project.json（Scratch内部形式）
        │     └─ schema.py の ALLOWED_OPCODES / extension_id_for_opcode を参照
        │
        └─ writer.py     … project.json + アセットバイナリ → .sb3（ZIP）出力
各モジュールの役割
モジュール	役割	主な依存
run.py	CLIエントリ。OpenAI/Gemini切替、指数バックオフ再試行、タイムスタンプ出力先生成	sb3gen.main
main.py	generate_sb3()。聞き返し(Clarification)ループを回しつつ apply_patch → compile_project → write_sb3 を直列実行	全モジュール
schema.py	ProjectSpec/SpriteSpec/BlockSpec/CostumeSpec/SoundSpec/ProcedureDefinitionSpec 等のPydanticモデル、ALLOWED_OPCODES（許可opcode一覧）、validate_project_spec（構造検証）	なし（最下層）
patcher.py	指示 → ActionPlan（計画） → 各アクション実行 → ProjectSpec 更新。聞き返し状態管理も担当	schema, llm_io, renderer, linter
llm_io.py	LLM出力のJSON化・スキーマ検証・「途中切れ」と「スキーマ違反」を判別した再試行、項目単位の分割生成	schema (Pydantic)
linter.py	スクリプトが参照する未知の変数/リスト/ブロードキャストを検出し、グローバル定義へ自動補完	schema
renderer.py	SpriteSpec を人間可読の疑似コードに変換（差分編集時にLLMへ現状を提示するため）	schema
assets.py	SVG自動生成（色・図形検出＋グラデーション合成）、WAV読込・解析、テンプレート管理、AssetRegistry	schema, patcher(型)
compiler.py	ProjectSpec → Scratch VM用 project.json。ブロックID採番、変数スコープ解決、mutation構築、拡張機能判定	schema, assets
writer.py	project.json＋アセットを .sb3（ZIP）に書き出し。欠落アセットの自動フォールバック	assets
2. 直近で追加・拡張された主要機能
① 複数スプライトの一括生成・編集（ActionPlan）
patcher.plan_instruction() がユーザー指示を ActionPlan（add_sprite / modify_sprite / remove_sprite / modify_globals の配列）に分解
apply_patch() が各アクションを 順次実行し、都度 reconcile_globals() で整合性を取りながら current_project を更新
途中のアクションが失敗しても、それまでの成功分は保持したうえで FAILED を返す（部分適用の耐障害性）
全体が曖昧な場合のみ clarification_needed=true とし、PendingClarification で最大3ターンまで聞き返し（MAX_CLARIFICATION_TURNS）。デフォルト進行の許可指示にも対応
② サウンド対応
schema.SoundSpec（name/data_format/asset_id/md5ext/rate/sample_count）
assets._parse_wav_info()：RIFF/WAVEヘッダーをチャンク単位で走査し、fmt チャンクからサンプルレート・チャンネル数・ビット深度を取得、dataチャンクからサンプル数を算出（チャンクのワード境界整列も考慮）
assets.register_wav_asset() / register_wav_template()：ファイルまたはバイト列からSoundSpecを登録
writer._collect_assets()：サウンド欠落時は _generate_silent_wav() による無音WAVへ自動フォールバック
compiler.compile_sprite()：sounds を project.json の sounds 配列へ出力（rate/sampleCountのデフォルト値補完込み）
③ スプライトローカル変数とグローバル変数の分離・解決
SpriteSpec.variables = そのスプライト専用のローカル変数（HP・スコア等）
CompileContext：_local_variable_ids（スプライト名→{変数名:ID}）と variable_ids（グローバル）を分離管理
resolve_variable()：アクティブスプライトのローカルを優先し、なければグローバルとして解決（未登録なら新規作成）
linter.reconcile_globals()：スクリプトが参照するがローカルにもグローバルにも存在しない変数/リスト/ブロードキャストを自動でグローバル定義に補完（「静かに動かないロジック」の防止）
プロンプト側（_MODIFY_SPRITE_SHELL_SYSTEM_PROMPT 等）でも「このスプライトだけの値はローカル、共有すべき値はグローバル」という方針をLLMに明示指示
④ rotationCenter自動推定とlayerOrder制御
assets._infer_svg_center()：SVGの viewBox または width/height から回転中心（幅・高さの半分）を正規表現で推定
AssetMaterializer._register_record() / register_default_backdrop() で生成時に自動セット
compiler.compile_project()：スプライトの登場順に layer_order（1から連番）を採番し layerOrder として出力。Stageは常に0
⑤ その他の追加機能・仕様
カスタムブロック（マイブロック）対応：ProcedureDefinitionSpec（name/arguments/warp/body）、proccode 自動生成、_build_mutation()、_compile_procedure()（procedures_definition/prototype/argument_reporter一式のコンパイル）。procedures_call のproc_name検証もschema層で実施
拡張機能（pen/music）自動判定：extension_id_for_opcode() によりopcode接頭辞から拡張IDを判定し、実際に使用されたものだけを project.json の extensions に宣言
LLM出力安定性（分割生成）：SpriteGenerationPlan（shell + script_plan要約のみ）→ スクリプトを1本ずつ個別LLM呼び出しで生成する2段階方式（_generate_sprite_chunked）。巨大JSON一括出力による途中切れを回避
途中切れ/スキーマ違反の判別リトライ：llm_io._is_likely_truncated() で末尾状態・エラー位置・メッセージから「途中切れ」を推定し、それぞれ専用のリトライプロンプトを構築
アセット生成の質向上：色・図形の複数検出＋放射グラデーション＋ハイライト＋接地影を持つSVG合成（最大4図形のグリッド配置）
堅牢なフォールバック：Stage自動生成時の背景を実際にレジストリ登録してからasset_idを発行（従来の固定ID使い回しバグの修正）、アセット欠落時のプレースホルダーSVG/無音WAV自動生成
sensing_keypressed 等の構造最適化：BLOCK_DEFS で inputs/fields を opcode ごとに明確化し、fields（KEY_OPTION等）と inputs（値ブロック差込）の扱いを分離整理
3. 処理フロー（指示入力 → .sb3出力）
① ユーザー指示（run.py CLI引数 or デフォルト文）
        │
② main.generate_sb3()
        │  ├─ apply_patch() ループ開始
③ patcher.plan_instruction()  … 指示を解析 → ActionPlan（アクション配列 or 聞き返し要求）
        │
   ├─[曖昧]→ NEEDS_CLARIFICATION → ターミナルで追加質問→回答 → PendingClarificationに履歴蓄積 → ③へ戻る（最大3ターン）
   └─[実行可]→
④ 各ActionSpecを順次実行（_execute_action）
    ├─ add_sprite    : _decide_assets()でアセット調達方針決定 → materialize_asset() → _generate_sprite_chunked()（shell+script_plan → スクリプト個別生成）
    ├─ modify_sprite : render_sprite_pseudocode()で現状提示 → _generate_sprite_chunked()で差分生成 → 既存asset_id引継ぎ
    ├─ remove_sprite : targetsから除去
    └─ modify_globals: GlobalsPatch生成 → 変数/リスト/ブロードキャストの追加・削除
        │  各アクション成功のたびに linter.reconcile_globals() で未定義参照を自動グローバル登録
        │  （schema.validate_project_spec() で都度、opcode許可・proc_name整合性等を検証）
        │
⑤ 全アクション成功 → PatchStatus.SUCCESS → ProjectSpec確定
        │
⑥ compiler.compile_project()
        │   ├─ Stage未定義なら自動生成（背景をレジストリ登録）
        │   ├─ CompileContextで変数/リスト/ブロードキャストID・ローカル変数スコープを管理
        │   ├─ 各スプライトをcompile_sprite()（ブロック木→project.json blocks、layerOrder付与）
        │   ├─ カスタムブロックをcompile_procedure()でhat+prototype+本体にコンパイル
        │   └─ 使用済み拡張機能をextensionsとして収集
        │
⑦ writer.write_sb3()
        │   ├─ _collect_assets()：project.json参照アセットをレジストリから収集（欠落時は自動フォールバック生成）
        │   └─ ZIPアーカイブとして project.json + 各アセットバイナリを書き出し
        │
⑧ .sb3ファイル完成

設計上の重要な特徴

段階的縮退：LLM出力を「入れ物(shell)＋計画」と「本体(スクリプト/カスタムブロック)」に分割し、1回の出力サイズを抑制（llm_io.py / patcher._generate_sprite_chunked）
部分失敗耐性：ActionPlanの途中で1アクションが失敗しても、それまでの成功分は破棄されず保持される
自己修復的検証：schema（構造）→linter（参照整合性）→compiler内検証（opcode許可・proc_name）→writer（アセット欠落フォールバック）と、複数層でプロジェクトが「壊れたsb3」にならないよう防御している

run.py の内容に基づいて、実行方法をまとめます。

実行方法まとめ（run.py）
1. 事前準備：APIキーの設定

使用するLLMプロバイダに応じて環境変数を設定します（どちらか一方でOK）。

OpenAIを使う場合

bash
export OPENAI_API_KEY="your_api_key_here"

Geminiを使う場合

bash
export GEMINI_API_KEY="your_api_key_here"
# または
export GOOGLE_API_KEY="your_api_key_here"

Gemini使用時は google-genai パッケージが必要です。

bash
pip install google-genai

モデル名は環境変数 GEMINI_MODEL で上書き可能（未指定時は gemini-3.6-flash）。

2. 基本の実行コマンド
bash
python run.py "画面中央に赤い丸の新しいスプライトを追加して、旗が押されたら10歩動かすプログラムを作って"

指示文（instruction）を省略した場合は、上記のデフォルト指示が使われます。

3. コマンドライン引数
引数	説明
instruction（位置引数）	生成指示の自然言語テキスト。省略可（省略時はデフォルト指示）
--provider {openai,gemini}	使用するLLMプロバイダを明示指定
--output <path>	出力先の .sb3 パスを指定

例：プロバイダを明示して実行

bash
python run.py --provider gemini "猫のスプライトを追加してジャンプさせて"

例：出力先を指定

bash
python run.py --output result.sb3 "旗クリックで音を鳴らすスプライトを作って"
4. プロバイダの自動判定ロジック（resolve_provider）

--provider を指定しなかった場合、以下の優先順位で自動判定されます。

--provider 引数（最優先、指定時のみ）
環境変数 LLM_PROVIDER（openai または gemini）
OPENAI_API_KEY があれば openai
GEMINI_API_KEY / GOOGLE_API_KEY があれば gemini
どれも無ければエラー終了し、設定方法を案内
bash
# LLM_PROVIDERで固定する例
export LLM_PROVIDER=openai
python run.py "指示文"
5. 出力先ファイル名（--output 未指定時）

generate_output_path() により、実行のたびに以下の形式で自動生成されます（既存ファイルは上書きしない）。

output_YYYYMMDD_HHMMSS.sb3

同名が既に存在する場合は output_YYYYMMDD_HHMMSS_1.sb3 のように連番が付与されます。

6. 実行中の対話（曖昧な指示の場合）

指示が曖昧で NEEDS_CLARIFICATION になると、main.generate_sb3() 内でターミナルに質問が表示され、input() で追加回答を求められます（最大3ターンまで）。

1. どのキャラクターを動かしたいですか？
2. 何色にしますか？
> （ここに回答を入力してEnter）
7. 一時エラー時の自動リトライ

with_retry() により、503 / 429 / RESOURCE_EXHAUSTED / timeout / overloaded 等が含まれるエラーは、指数バックオフ（初期2秒→倍々）で最大5回まで自動再試行されます。それ以外のエラーは即座に失敗として終了します。

8. 実行結果

成功時:

使用プロバイダ: openai
指示を実行中: <指示文>
生成が完了しました: output_20260813_153000.sb3

失敗時は標準エラー出力にメッセージを表示し、終了コード1で終了します。
